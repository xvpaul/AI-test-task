# CI/CD: автодеплой конфига на VPS

Что делает пайплайн на push в `main`:

1. **Bootstrap** — на сервере клонирует репозиторий OpenClaw, если его ещё нет,
   создаёт каталог конфига и пишет `.env` для compose. Идемпотентно: на повторных
   запусках ничего не пересоздаёт.
2. **Рендер** — подставляет секреты в `openclaw.config.template.json5`.
3. **Доставка** — заливает конфиг и `SOUL.md` на VPS.
4. **Перезапуск** — `docker compose up -d openclaw-gateway` и вывод логов.

Свой образ не собирается — используется готовый `ghcr.io/openclaw/openclaw:latest`.

Благодаря шагу 1 первичная установка не требует ручных действий на сервере: достаточно
чистой машины с `docker` и `git`. Если они не установлены, bootstrap остановится
с понятным сообщением — поставьте их разово:

```bash
curl -fsSL https://get.docker.com | sh
apt-get install -y git
```

> ⚠️ **Bootstrap намеренно не запускает `scripts/docker/setup.sh`.** Тот скрипт
> интерактивный, и хотя в документации описан headless-режим
> (`OPENCLAW_SKIP_ONBOARDING`, флаги `--non-interactive`, `--accept-risk`, `--skip-health`),
> проверить точный набор флагов по исходнику не удалось. Вместо этого bootstrap делает
> то, что можно проверить: клонирует репозиторий, пишет `.env` и поднимает compose,
> а конфигурацию мы и так формируем сами из шаблона. Если контейнеру всё же понадобятся
> артефакты онбординга, это будет видно в логах первого запуска — тогда добавим шаг.

## 1. Ключ для деплоя

Отдельный SSH-ключ **только для CI** — не используйте свой личный.

Подставьте свой порт вместо `2222`. Если SSH на стандартном 22 — флаги `-p`/`-P`
можно опустить, а секрет `VPS_PORT` не задавать.

```bash
# На локальной машине
ssh-keygen -t ed25519 -f ~/.ssh/openclaw_deploy -N "" -C "github-actions-openclaw"

# Публичную часть — на VPS
ssh-copy-id -p 2222 -i ~/.ssh/openclaw_deploy.pub user@ваш-сервер

# Проверить, что заходит без пароля
ssh -p 2222 -i ~/.ssh/openclaw_deploy user@ваш-сервер 'echo OK'
```

Снять отпечаток сервера для `known_hosts` (защита от MITM — без него CI будет
доверять любому серверу, который ответит на этот адрес):

```bash
ssh-keyscan -p 2222 -t ed25519 ваш-сервер
```

> ⚠️ **Порт обязательно указывать и здесь.** Для нестандартного порта `ssh-keyscan`
> выдаёт запись в формате `[ваш-сервер]:2222 ssh-ed25519 AAAA...` — с квадратными
> скобками и портом. Запись, снятая без `-p`, будет для порта 22 и к вашему серверу
> не подойдёт: деплой упадёт с `Host key verification failed`.
> Копируйте вывод целиком, как есть.

## 1a. Порты: где какой флаг

Частый источник потерянного времени — у `scp` и `ssh` флаги порта различаются регистром:

| Команда | Флаг | Пример |
|---|---|---|
| `ssh` | `-p` строчная | `ssh -p 2222 user@host` |
| `scp` | `-P` заглавная | `scp -P 2222 file user@host:/path` |
| `ssh-keyscan` | `-p` строчная | `ssh-keyscan -p 2222 host` |
| `ssh-copy-id` | `-p` строчная | `ssh-copy-id -p 2222 -i key.pub user@host` |

В `deploy.yml` это уже учтено — менять ничего не нужно.

## 2. Секреты в GitHub

`Settings → Secrets and variables → Actions → New repository secret`:

| Секрет | Значение |
|---|---|
| `GEMINI_API_KEY` | ключ из AI Studio (**новый**, не тот, что был в переписке) |
| `TELEGRAM_BOT_TOKEN` | токен от `@BotFather` |
| `TELEGRAM_OWNER_ID` | ваш numeric ID |
| `VPS_HOST` | IP или домен сервера |
| `VPS_USER` | пользователь на сервере |
| `VPS_PORT` | SSH-порт. **Необязательный** — если не задать, используется `22`. Сделан секретом, а не переменной: секреты маскируются в логах Actions |
| `OPENCLAW_GATEWAY_TOKEN` | Токен для входа в дашборд. **Необязательный** — если не задать, bootstrap сгенерирует его сам при первом запуске и сохранит в `.env` на сервере (посмотреть: `grep TOKEN ~/openclaw/.env`). На повторных деплоях не перезаписывается |
| `VPS_SSH_KEY` | содержимое `~/.ssh/openclaw_deploy` (приватный ключ, **целиком**, вместе со строками `BEGIN`/`END`) |
| `VPS_KNOWN_HOSTS` | вывод `ssh-keyscan` из шага 1 |

Во вкладке **Variables** (не Secrets) можно задать необязательные:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `OPENCLAW_DIR` | `$HOME/.openclaw` | Каталог на хосте, смонтированный в контейнер |
| `COMPOSE_DIR` | `$HOME/openclaw` | Куда клонируется репозиторий с `docker-compose.yml` |
| `OPENCLAW_IMAGE` | `ghcr.io/openclaw/openclaw:latest` | Образ; можно закрепить конкретный тег |
| `TELEGRAM_DM_POLICY` | `allowlist` | Режим доступа к личке. `allowlist` — только владелец, `pairing` — по одобрению, `open` — все, `disabled` — никто. Недопустимое значение роняет деплой на рендере |

> Если OpenClaw уже стоял на сервере до подключения CI, проверьте реальные пути
> (`docker compose ls`, `docker compose config | grep -A3 volumes`) и переопределите
> переменные — иначе bootstrap склонирует вторую копию рядом.
>
> `allowFrom` в шаблоне намеренно оставлен пустыми скобками: список собирается
> в workflow из `TELEGRAM_DM_POLICY`. Иначе переключение режима одной переменной
> давало невалидную пару — `open` проходит валидацию только со звёздочкой в списке,
> а `allowlist` требует конкретный numeric ID.
>
> Задавать пути со знаком `~` можно: bootstrap раскрывает тильду на сервере.
> Именно поэтому дефолты вычисляются там, а не в workflow — переданная в кавычках
> тильда не раскрылась бы и создала каталог с именем `~`.

## 3. Инициализировать репозиторий

```bash
cd /home/xvpaul/Desktop/test_tasks/vibecoder_agency
git init -b main
git add .
git status              # ← убедиться, что openclaw.config.json5 НЕ в списке
git commit -m "OpenClaw: конфиг, SOUL.md, деплой на VPS"

gh repo create openclaw-gateway --private --source=. --push
```

Репозиторий делайте **приватным**. Секретов в нём нет, но лишний раз публиковать
конфигурацию своего сервера незачем.

## 4. Запустить

Первый деплой — вручную: вкладка **Actions → Deploy OpenClaw config → Run workflow**.
Дальше срабатывает автоматически на каждый push, меняющий шаблон или `SOUL.md`.

Успешный прогон заканчивается выводом `docker compose ps` и последних 30 строк логов —
по ним сразу видно, поднялся ли Gateway.

## Что защищено и что нет

Пайплайн намеренно устроен так:

- **Секретов в репозитории нет** — только шаблон с плейсхолдерами
- **`known_hosts` из секрета**, а не `ssh-keyscan` в момент деплоя — иначе CI доверял бы
  первому ответившему серверу
- **Проверка плейсхолдеров** — если секрет не задан, деплой падает на рендере,
  а не заливает на сервер конфиг с буквальным `${GEMINI_API_KEY}`
- **`up -d`, а не `restart`** — restart не перечитывает переменные окружения
- **Ключ удаляется** на шаге с `if: always()`, даже если деплой упал

Чего пайплайн не делает: не откатывается автоматически при неудаче и не проверяет,
что бот реально отвечает — только что контейнер запустился. Для тестового задания
этого достаточно; в продакшене нужен health-check и rollback.

## Если деплой падает

| Ошибка | Причина |
|---|---|
| `Host key verification failed` | `VPS_KNOWN_HOSTS` пустой, от другого хоста, либо снят без `-p` при нестандартном порте (нужен формат `[host]:port`) |
| `Connection refused` / таймаут | Неверный `VPS_PORT`, либо порт закрыт файрволом провайдера |
| `Permission denied (publickey)` | Приватный ключ скопирован не целиком, либо публичная часть не попала на сервер |
| `secret ... не задан` | Пропущен секрет из таблицы в шаге 2 |
| `scp: No such file or directory` | Неверный `OPENCLAW_DIR` — проверьте реальный путь тома на сервере |
| `client_loop: send disconnect: Broken pipe` | Соединение оборвалось на долгой операции. В `~/.ssh/config` раннера выставлен keepalive; если повторяется — смотрите нагрузку и сеть на VPS |
| `существует, не пуст и не является git-репозиторием` | Остаток от прерванного клонирования. Проверьте `ls -la` каталог и удалите, если это мусор |
| Контейнер поднялся, бот молчит | Это уже не CI — смотрите логи и таблицу проблем в `DEPLOY.md` |
